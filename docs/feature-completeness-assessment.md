# 恩典同行：功能完整度與擴充優先級評估

**評估日期：2026-08-15（GMT+8）**  
**評估範圍：現有網站功能、角色控制、資料作業、行動版操作及後續導入風險**

## 結論摘要

目前系統已具備一套**可供小型至中小型教會內部試行**的牧養行政 MVP。它能管理宣教士、支持承諾、代禱、小組名冊、聚會出席、關懷紀錄、活動、公告與三層角色權限；對於由 Admin 與少數 Leader 使用、且仍在導入資料與校準流程的情境，功能已足夠啟動。

不過，若要作為**長期正式營運的教會核心系統**，目前尚不宜直接承擔財務憑證、敏感牧養資料的高風險治理，或大量會友的全生命週期管理。首要原因並非 CRUD 功能不足，而是資料治理、備份還原、稽核、中央人員主檔、通知工作流與進階權限尚未成型。商用及開源教會管理工具通常把保密群組、個人參與分析、通知、備份還原、帳號權限與財務資料視為獨立且成熟的模組。[1] [3]

> **建議判斷：**現階段可進行「受控試行」；完成 P0 項目後，才適合進入正式行政使用；完成 P1 項目後，才適合作為牧養與小組營運的日常工作平台。

## 現況功能盤點

| 領域 | 已完成能力 | 適用程度 | 評估 |
| --- | --- | --- | --- |
| 宣教士管理 | 個人檔案、照片、服事地區、差派機構、聯絡方式、啟用／停用、搜尋與篩選。 | 受控試行 | 已滿足名冊管理核心。 |
| 支持者與承諾 | 支持者主檔、支持金額與頻率、每月等值支持概覽。 | 試行 | 可管理承諾，但尚非正式捐款帳或對帳系統。 |
| 代禱管理 | 依宣教士建立、代禱中／已回應／已歸檔、可恢復顯示。 | 良好 | 已具明確閉環；仍缺責任人與提醒。 |
| 小組牧養 | 小組、帶領人、成員、聚會、逐次出席、出席率、關懷日誌。 | 良好 | 已能支援 Leader 的基本週期性作業。 |
| 活動與公告 | 活動建立、目標小組、月曆、公告與近期活動摘要、搜尋。 | 試行 | 已有資訊發布；尚未有 RSVP、報名與簽到。 |
| 權限與安全 | Admin／Leader／Member、後端程序檢查、受限頁導回與提示。 | 良好起點 | 已避免基本越權，但仍需細緻化、稽核化。 |
| 體驗與品質 | 繁中、桌面／行動版、搜尋篩選、空狀態、14 項自動化測試。 | 良好 | 適合開始蒐集實際同工回饋。 |

## 關鍵缺口與為何重要

| 缺口 | 為何應補齊 | 建議處置 |
| --- | --- | --- |
| 備份、還原與資料匯出 | 牧養、關懷和支持資料一旦遺失，復原成本高；成熟教會系統通常將 Backup & Restore 視為管理面向。[3] | 建立排程備份、可下載 CSV／JSON 匯出、還原演練及資料擁有人規範。 |
| 稽核紀錄與帳號生命週期 | 目前可調整角色與敏感資料，但缺少「誰在何時修改了什麼」的證據。 | 加入 audit log、帳號停用、角色異動雙重確認及 Admin 操作紀錄。 |
| 中央人員／家庭主檔 | 小組成員、支持者與宣教士目前是不同資料脈絡，未來容易重複或難以看見整體參與。人員與家庭檔案是常見教會管理核心。[3] | 建立 `people` 與 `households` 主檔，並讓小組、關懷、活動與支持關聯至同一人。 |
| 細緻保密權限 | 恢復、悲傷、醫治或特定關懷小組需要隱藏名冊與限制帶領人之外的存取；保密群組是成熟群組工具的重要能力。[1] | 加入小組保密級別、成員匿名化、欄位層級遮罩和最小權限配置。 |
| 跟進任務與提醒 | 代禱、關懷、缺席與支持者聯繫都有「下一步」；單靠歷史紀錄會讓重要跟進流失。支持者關係工具會把任務、互動與給付模式通知納入日常工作。[2] | 建立待辦、責任人、到期日、提醒和逾期清單；先做關懷與缺席提醒。 |
| 真實支持／捐款對帳 | 支持承諾並不等於實收捐款；切勿以目前資料直接產生收據、抵稅或財務報表。 | 將「承諾」與「實收」分表，建立匯入、對帳、異常提示與財務授權流程。 |
| 活動生命週期 | 現有月曆可發布活動，但尚無報名、候補、容量、RSVP、簽到與活動後追蹤。成熟群組工具會提供活動 RSVP、資源與群組參與追蹤。[1] | 先做 RSVP、報名名單與活動簽到；再加入容量、候補與 QR code。 |
| 溝通與整合 | 公告尚停留在站內；實際動員常需 LINE、Email、行事曆與會友資料同步。MPDX 將聯絡資訊、行事曆與通訊服務同步視為降低行政負擔的方法。[2] | 先設計通知偏好與站內通知，再評估 LINE、Email、Google Calendar 的單向整合。 |
| 營運報表 | 現有為總覽與出席率；尚未能看見連續缺席、成員留存、新來者、未完成關懷與支持落差。 | 建立依角色可見的健康指標、週報與 CSV 匯出，避免先做過度複雜的 BI。 |

## 優先級路線圖

| 優先級 | 建議項目 | 價值 | 實作依賴 | 建議時點 |
| --- | --- | --- | --- | --- |
| **P0：正式導入前** | 備份／還原、資料匯出、稽核紀錄、帳號停用、個資保留與刪除規則。 | 保障資料可用性與問責。 | 無。 | 立即。 |
| **P0：正式導入前** | 支持承諾與實收捐款分離、匯入及對帳權限。 | 避免把牧養承諾誤作財務憑證。 | 財務流程確認。 | 正式處理金流前。 |
| **P1：日常牧養效率** | 關懷／缺席／代禱待辦、責任人、到期提醒、週期報表。 | 避免人被遺漏，縮短同工交接。 | 通知設計。 | P0 後。 |
| **P1：資料品質** | People／Household 主檔、CSV 匯入、重複資料偵測與合併。 | 形成單一真實來源。 | 資料清理規則。 | P0 後。 |
| **P1：活動閉環** | RSVP、報名、簽到、容量與活動出席報表。 | 將公告轉為可量測的參與。 | 中央人員主檔較佳。 | P1 同期。 |
| **P2：深化牧養與互動** | 保密群組、資源庫、群組討論、Leader 交接摘要。 | 提升敏感牧養與群組黏著。 | 細緻權限、檔案儲存。 | P1 後。 |
| **P2：外部整合** | LINE／Email、Google Calendar、支持資料系統同步。 | 減少重複輸入與提升動員率。 | 個資同意、通知偏好、錯誤處理。 | 流程穩定後。 |
| **P3：進階分析** | 參與趨勢、流失風險、牧區健康儀表板、資料倉儲。 | 支援策略與資源配置。 | 穩定且乾淨的主資料。 | 有連續 6–12 個月資料後。 |

## 依導入規模的適用性

| 導入情境 | 現在是否足夠 | 最低必要條件 |
| --- | --- | --- |
| 約 50 人以下、僅同工內部使用 | **大致足夠試行** | 指定資料管理者、手動備份及不把支持承諾當正式捐款帳。 |
| 約 50–300 人、有多個小組與數位 Leader | **部分足夠** | 先完成 P0，並優先完成關懷待辦、缺席提醒與人員主檔。 |
| 超過 300 人、含敏感關懷、正式金流或跨堂點 | **尚未足夠正式上線** | 完成 P0＋P1，加入保密群組、稽核、資料治理與整合錯誤處理。 |

## 建議的下一步

建議先由教會確認兩個決策：第一，系統是否只管理「牧養行政」還是也要承擔「正式財務／奉獻」；第二，誰是每一類資料的擁有人與審核者。若近期要正式導入，下一個開發迭代應優先處理 **P0 的備份、稽核與資料匯出**，再做 **P1 的關懷待辦與人員主檔**。這樣能保留目前系統的簡潔，同時避免過早投入高風險整合。
